1.개요
 - Redis는 데이터를 메모리에 보관하기 때문에 인스턴스가 셧다운 될 경우 모든 데이터가 유실된다.
   Redis는 메모리에 로드된 데이터를 디스크에 저장을해 이 문제를 해결할 수 있다.

2.방식 별 메커니즘
(1)RDB
  - 동작방식
    => RDB는 주기적으로 snapshot을 생성해 특정 파일(**.rdb)로 저장한다. 저장 시 압축할 수 있으므로 데이터의 크기가 AOF방식에 비해 작다.
    => 별도의 설정(snapshot주기, 디렉터리, 파일명 등)을 하지 않더라도 특정 조건에 의해 동작한다.
       특정 조건이란? 최소 10,000개 변경 후 1분이 지날경우, 100회 이상 변경 후 5분이 지날 경우, 1회 이상 변경 후 1시간 후
       파일은 인스턴스 동일한 디렉터리에 dump.rdb로 저장된다.(경로와 파일명은 변경이 가능하다)
  - 장점 : RDB파일은 용량도 작도 바이트로 저장하되기 떄문에 rdb를 통한 레디스 기동 시 빠른 복구가 가능하다.
  - 단점 : 전체 snapshot을 뜨는 것은 레디스 자체에 버든이 될 수 있으므로, 실시간이 아닌 주기를 설정해 스냅샷을 찍는다. 만약 스냅샷 찍은 후 일정 시간동안 운영하다 셧다운 될 경우, 스냅샷 이후 데이터는 유실된다.
  - 관련 설정
* save
  => rdb 스냅샷을 찍는 주기를 설정한다. 레디스는 별도의 설정을 하지 않아도 위에서 설명한 특정 조건으로 스냅샷을 찍는데 이 설정을 표현하자면 save 3600 1 300 100 60 10000 와 같다.
     save 3600 1 는 and 조건으로 1건이 변경된 경우 바로 스냅샷을 찍는 것이 아닌 1시간 후에 찍게된다. 
     save ""  를 하면 rdb 스냅샷을 off한다.
* stop-writes-on-bgsave-error parameter(default:yes)
  => rdb 파일 저장 실패 시 데이터를 받을지 결정하는 설정이다. 기본 값은 데이터를 받지 않는 것이다. 그 이유는 RDB파일이 저장되지 않을 때 관리자에게 문제 상황을 빨리 알려주는데 의의가 있다.
* rdbcompression 
  => rdb파일 저장 시 LZF 방식으로 압축할지 정한다. 기본 값은 yes이며 압축작업에 대한 cpu사용 부담이 있을 경우 no로 설정한다. 
* rdbchecksum
  => RDB 파일이 정확히 저장되었는지 확인하는 방법으로 checksum을 파일 끝에 추가할 수 있다. 이기능을 이용하면 파일 정확성을 높일 수 있다. 하지만 파일을 저장 및 로딩 시 10% 정도성능이 저하될 수 있다.
* sanitize-dump-payload
  => RDB파일 혹은 restore파일 등으로 로딩할 때 ziplist, listpack에 대한 정합성 및 validation 검사 수행 (default:no)
* dbfilename
  => 파일명
* dir
  => 디렉터리 경로
* rdb-del-sync-files
  => 복제 시 사용한 rdb파일을 삭제한다. 레디스 마스터에서 스냅샷 작업을 false로하면 rdb파일이 생성되지 않으나 복제 작업으로 인해 생성된 rdb파일이 있으면 사용자에게 혼선을 주기 때문이다.


(2)AOF
  - 동작방식
    => AOF는 append only file의 약자로 레디스에 write하는 명령어를 파일로 기록해 백업하는 방식이다.
  - 장점
    => 매 초마다 
  - 단점
  - 관련 설정
    * appendonly 
      => AOF 모드를 수행할지 설정한다. 
    * appendfilename 
      => aof파일 이름이며, appendonly가 켜져있을 때 동작한다. 위치는 dir에 설정된 값이다.
    * appendfsync
      => aof파일에 쓰는 주기를 설정한다. 값은 no, everysec, always가 있다. 참고로 always는 모든 write명령어 마다 파일에 쓰기 때문에 성능에 영향을 미친다.
        Step 1: 클라이언트가 레디스 서버로 데이터를 보내다. 데이터는 현재 클라이언트 메모리에 있다.
        Step 2: 레디스 서버가 데이터를 받는다. 데이터는 서버 메모리에 있다.
        Step 3: 레디스 서버가 데이터를 디스크에 쓰는 write() 시스템 콜을 호출한다. 데이터는 커널 버퍼에 있다.
        Step 4: 운영체제(OS)는 fsync() 시스템 콜을 호출해서 버퍼에 있는 데이터를 디스크 제어기(controller)에 쓴다. 데이터는 디스크 케시(cache)에 있다.
        Step 5: 디스크 제어기는 물리적으로 디스크에 기록한다.
        레디스 서버는 Step 3에서 write() 데이터를 디스크에 쓰기 위해 fsync() 시스템 콜을 호출한다.   이 fsync()는 Step 4를 제어한다. Step 5는 일반적으로 디스크 제어기가 알아서 한다.   Appendfsync 파라미터는 fsync()를 호출하는 시점을 정한다.
        
        always: 레디스 명령이 실행될 때 마다 디스크에 쓴다. 성능이 매우 떨어진다. 아주 특별한 경우가 아니면 권하지 않는다.
        everysec: 데이터를 모아서 1초 마다 디스크에 쓴다. Write()와 fsync() 시스템 콜 호출의 지연 시간에 따라서 최대 2초 이내의 데이터를 잃어 버릴 수 있지만, 성능과 데이터 보존 양 측면에서 적절한 값이다.   기본값이다.
        no: 디스크에 쓰는 시점을 운영체제(리눅스)에 맡긴다.   대부분의 리눅스 시스템에서는 30초 마다 디스크에 저장된다. 그러므로 운이 나쁠 경우 최대 30초간의 데이터를 유실할 수 있다.
    * no-appendfsync-on-rewrite 
      => 레디스에서 대량의 데이터를 파일에 쓰는 경우에 성능에 따라 많은 시간이 필요할 수 있다. 이 시간동안 fsync()를 수행해 문제가 발생할 수 있다.
         appendfsync 파라미터를 everysec이나 always로 설정했을 때 fsync()를 수행한다. no-appendfsync-on-rewrite 값을 yes로하면 레디스 서버에서 fsync()를 직접 수행하지 않고 운영체제에 맞긴다. 운영체제는 30초 간격으로 fsync를 수행한다.
    * auto-aof-rewrite-percentage
      => AOF 파일의 다시쓰기(Rewrite)하는 시점을 정합니다.   이 파라미터 값을 100으로 했다면(기본값) 이전 다시쓰기한 다음 AOF 파일 크기가 100% 증가했으면 다시쓰기를 합니다.   다시쓰기는 내부적으로 BGREWRITEAOF 백그라운드 프로세스가 호출되어 수행됩니다.   만약 처음 다시쓰기를 하는 상황이면 레디스 서버 시작시 AOF 파일 크기를 기준으로 합니다.
    * auto-aof-rewrite-min-size
      => AOF 파일 크기가 이 파라미터에서 설정한 값 이상이 되어야 다시쓰기(Rewrite)를 한다. 
    * aof-load-truncated
      => 레디스 시작 시 AOF 파일을 메모리로 로드할 때 AOF 파일 끝이 잘린(truncated)것을 발견할 수 있다. 레디스가 실행중에 크레시(crash), 특히 ext4 파일시스템을 data=ordered 옵션없이 마운트된 경우(레디스가 크레시 되었지만 운영체제가 여전히 올바르게 동작하고 발생하지 않습니다) 발생할 수 있다.
        yes로 설정 시 데이터를 로드하고, 오류는 로그에 남긴다. 레디스 기동은 성공한다.
        no로 설정 시 데이터로드를 중단하고, 레디스 기동이 되지 않는다.
    * aof-use-rdb-preamble
      => rewrite시 rdb format으로 파일을 쓸지 여부를 설정. 그 이유는 AOF파일 사이즈를 줄일 수 있고 write, load 시간도 줄일 수 있기 때문이다.
    * aof-timestamp-enabled    
      => AOF파일은 저장된 시점을 알 수 없다. 해당 기능을 키면 타임스탬프 값을 알 수 있다. 이 타임스탬프 값을 이용해 해당 시점으로 복구가 가능하다.

- rdb파일에는 1000개의 데이터가 있다. AOF파일에는 5개의 데이터가 있다. 이경우 기동하면 레디스는 비어 있다.
- 두 설정다 on이 가능하다. 복구할 떄 어느 파일로 하는지는 찾아봐야 하지만 rdb로 예상함.
